aweSOM at GRMHD scale: bug fixes, a frozen model artifact, exact inference, and parallel batch training

Eight deterministic bugs are fixed, a trained self-organizing map can now be exported as a language-neutral table that a C++ code reproduces bit for bit, inference runs about 15 times faster, and a JAX batch trainer shards training data across every visible GPU. All work sits on the branch research/grmhd-scale in a separate checkout and nothing has been pushed.

Summary

The mandate was to optimize and fix bugs in aweSOM, to make training run on parallel GPUs, and to improve the SOM-to-data mapping so that a pretrained lattice can be handed to an AsterX run as a table and used to track features at runtime. The user-authored contract for that link, in the AsterX audit notes (Ha 2026, ideas.md section 4), fixes the shape of the solution: training stays offline in Python, the artifact must be language-neutral and carry the feature specification, scaler, weights, node-to-cluster map, uncertainty thresholds and provenance, and the thorn (provisionally AsterCurrentSheets) does only feature evaluation and best-matching-unit inference.

Bugs

8 fixed with regression tests, 2 pre-existing quirks recorded as open. See section 1.

Model artifact

SOMModel in HDF5 and plain text; header-only C++ classifier reproduces Python labels bitwise. See section 2.

Inference

Chunked numba kernel, 1.8 million points per second on this laptop versus 0.12 million before, identical labels. See section 6.

Parallel training

JAX batch map over a device mesh; passes the pre-registered quantization and topographic error acceptance against the online trainer. See section 3.

Uncertainty. No GPU was available in this session. The multi-device path was exercised on four virtual CPU devices and on two CPU processes; GPU throughput, the SLURM script and multi-node runs are untested. Every design decision was taken without the user present and is listed in section 7.

2. Frozen model artifact and exact inference

What is stored

aweSOM.model.SOMModel (src/aweSOM/model.py) freezes a trained lattice with everything a runtime consumer needs and nothing it does not: lattice shape and weights, the fitted Scaler, the node-to-cluster table, per-node and global distance thresholds, the feature names, and provenance (format version, aweSOM version, git commit, creation time, seed, training length, merge threshold, dataset string). save() writes HDF5; save_text() writes a self-describing text table with # key value header lines followed by one row per node, so a code without HDF5 can parse it with the standard library. SOMModel.load reads either.

The scaler is stored in one form regardless of how it was fitted:

x′=x−offsetscalex' = \frac{x - \mathrm{offset}}{\mathrm{scale}}

For the "manual" kind, offset is the per-feature mean and scale is twice the standard deviation divided by bulk_range, matching run_som.manual_scaling. The two are bitwise equal when bulk_range is a power of two (1.0 is the only value the package uses) and agree to one rounding otherwise, because the division and multiplication round differently. A "minmax" kind and an identity kind exist too.

Uncertainty thresholds

Following the audit contract, each model carries node_dist_q99 (the 99th percentile of the Euclidean BMU distance of the training points that mapped to that node) and reject_distance (the 99.9th percentile over all training points). A runtime cell whose distance exceeds either can be flagged as unlike the training sample; the C++ header exposes this as is_unfamiliar. The percentiles are a design choice (assumption A6), not a calibrated detector.

Exactness contract

The GPT Sol numerical check (source ledger section E) compared four BMU arithmetic variants on a 2368 by 6 random lattice and one million points against float64 direct differences: float32 direct gave 0 disagreements, float64 expansion 0, float32 expansion 11 (rate 1.1 × 10−5). The reference path is therefore defined as float64 direct differences, sequential feature sum, strict less-than scan in ascending node index, which is what NumPy argmin returns on ties:

c(x)=argmini∑f=1F(wif−xf)2c(x) = \operatorname*{argmin}_i \sum_{f=1}^{F} (w_{if} - x_f)^2

Three implementations follow it and are tested against each other: aweSOM.inference.best_match_nodes (numba, parallel over points, chunked, no per-point allocation), the original Lattice.best_match kernel (kept as _best_match_legacy), and cpp/awesom_classify.hpp. On the committed fixture (10 by 8 lattice, 4 features, 1000 points, tests/fixtures/) the C++ program's labels and distances equal the Python output exactly, and the test compiles and runs it with the system compiler when one is available (tests/cpp_test.py). Lattice.best_match now delegates to the new kernel and keeps its (N, 1) float output; Lattice.predict returns int32 labels, optionally with distances, without the two full-size intermediates of the old map-then-assign sequence.

Evidence. On 2 million random points the new kernel and the legacy kernel returned identical labels (measured in this session, see Table 4). Float32 input is accepted and documented as approximate: genuine ties may flip.

3. Parallel batch training in JAX

The online trainer updates the lattice one sample at a time, so it cannot be split across devices without changing the algorithm. The batch map (Kohonen 2001; Fort, Letremy and Cottrell 2002) replaces the per-sample update with one fixed-point step per epoch:

wi=∑jh(cj,i)xj∑jh(cj,i)w_i = \frac{\sum_j h(c_j, i)\, x_j}{\sum_j h(c_j, i)}

where cj is the BMU of sample j under the weights at the start of the epoch and h is the Gaussian neighbourhood of Lattice.Gamma on Chebyshev lattice distance with the learning rate set to 1 (it cancels). The sums are factorised through per-node partial sums S and hit counts n (jax.ops.segment_sum on each device), combined with lax.psum over a one-dimensional jax.shard_map mesh, and then W = HTS / HTn with H[c, i] = h(c, i). Nodes with zero denominator keep their weight, which matches the online rule when all increments vanish (Sol, ledger E). pmap was not used because JAX 0.12 lists it as maintenance-only (JAX changelog; shard_map guide).

Schedule and precision

Default 40 epochs: radius rmax = max(xdim, ydim) + 1 for the first half, linear to rmin = 8 over the third quarter, rmin for the last quarter, the same proportions as the online schedule. Sol flagged this budget as uncertain until measured at 20, 40 and 80 epochs; that sweep was not run. Distances use float32 with Precision.HIGHEST (no TF32); per-node sums, counts and the master weights are float64 inside a scoped enable_x64. The agent found that float32 sums made 1-device and 4-device results differ by 1.4 × 10−4 after ten epochs because near-tied BMUs amplify last-bit summation-order differences; with float64 sums 1, 2 and 4 devices gave bitwise-identical weights.

Acceptance against the online trainer

The acceptance criterion was fixed before implementation (self-grill Q11, Sol bounds): over five paired seeds on a synthetic three-cluster set, the upper confidence bound (mean + 2.7764 · sd / √5) of the quantization error ratio minus one must be at most 0.03 and of the topographic error difference at most 0.01. Quantization error is the mean distance to the BMU; topographic error is the fraction of samples whose two best nodes are not 8-neighbours.

Usage

from aweSOM import Lattice
som = Lattice(64, 37, 0.1, train=0)
info = som.train_lattice_batch(data, feature_names, epochs=40)   # all visible devices
labels = som.predict(new_snapshot, merge_cost=0.2)

# multi-GPU, one process per GPU (examples/slurm_scripts/submit_batch_gpu.slurm):
import jax; jax.distributed.initialize()        # SLURM auto-detected
weights, info = train_batch(local_rows, xdim, ydim)   # data = process-local rows

import aweSOM does not import JAX; aweSOM.batch raises a clear ImportError without it, and pip install aweSOM[gpu] pulls jax[cuda12]. Multi-host initialisation is the caller's job, as recommended in the JAX multi-process documentation (JAX multi-process guide).

Limitation. The four virtual CPU devices share the same cores, so the CPU benchmark (0.55 to 0.66 million points per second per epoch at 2 million points, 64 by 37 lattice) tests sharding correctness, not speed. GPU scaling is unmeasured. Determinism on GPU requires XLA_FLAGS=--xla_gpu_exclude_nondeterministic_ops=true because scatter-add uses atomics (OpenXLA determinism note). Apple Metal is not supported: jax-metal last shipped for JAX 0.4.34.

4. Online trainer and centroid merge, same results faster

train_lattice gains history=True; with the default, lattice and U-matrix snapshots every save_frequency steps are kept exactly as before, because the plasma and iris notebooks read lattice_history from unpickled objects (ledger F). The per-step BMU search and neighbourhood update were moved into one numba kernel that touches only nodes inside the radius, with the Gaussian written inline in the same operation order as Gamma. The schedule (alpha decay, radius shrink) is precomputed up front. The result is bitwise identical to the previous loop on seeded runs across sampling and alpha types (tests/fast_som_test.py, 32 tests, including a check that the summation order matches NumPy's pairwise sum for 8 or more features).

merge_similar_centroids was recursive and recomputed every pairwise line cost on each round. Sol showed that a single greedy pass with a frozen normaliser is not equivalent (counter-example in ledger E), so the replacement is a loop that reproduces the recursion exactly: recompute representatives and counts, read costs from an ordered-pair cache, stable-sort, normalise by the current maximum, stop when the smallest normalised cost reaches the threshold, otherwise merge the smaller-count centroid into the larger. On 20 random maps at three thresholds the new loop gives the same centroids, counts and cluster assignment as the old recursive code; on a 60 by 40 lattice with 274 centroids and 268 merges it succeeds under a recursion limit that makes the old code fail.

5. AsterCurrentSheets thorn design

The thorn itself belongs in the AsterX repository, which was read-only for this session. The design document docs/source/astercurrentsheets.md fixes the contract from verified AsterX conventions gathered by the index sweep (ledger A, every claim with file and line): cell-centred {ccc} grid functions tagged checkpoint="no", grid.loop_int_device<1,1,1> kernels, scheduling AT analysis AFTER AsterAnalysis_MHD, a one-time table load AT CCTK_WRAGH following the EOSX pattern (CCTK_STRING parameter, rank-0 read, MPI_Bcast, The_Managed_Arena allocation, amrex::Gpu::copy), and output through CarpetX::out_silo_vars.

One fact shapes the feature set: AsterX has no current density or curl-B grid function; the only curl in the code is B = curl A onto staggered faces. The thorn must therefore compute a curl-B proxy from cell-centred HydroBaseX::Bvec with central differences (one ghost layer). The doc proposes six per-cell features (jmag, jpar, jperp, bmag, rho, beta_inv), notes that the smoothed and oriented-kernel features of the published PIC pipeline cannot be evaluated per cell, requires the thorn to abort on a feature-name mismatch with the table, and lists the validation steps the audit demands: offline/runtime label equivalence and measured overhead before any extension.

7. Decisions taken without the user

Each was recorded in the self-grill notes before implementation (planning/notes/2026-10-26-self-grill.md, Q1 to Q15). The user can overturn any of them; the affected code is small and isolated.

  1. A1, parallel training means the batch map. Running many online realizations one per device needs no new code (the SCE scripts already use multiprocessing). The new feature is a different estimator; equivalence is statistical, not bitwise.
  2. A2, batch schedule and acceptance thresholds. 40 epochs with the online radius proportions; 3% quantization error and 0.01 topographic error bounds over five seeds. These were chosen to be strict but passable, not derived from the physics.
  3. A3, artifact format. HDF5 primary with a plain-text twin; one scaler formula; node index x + y · xdim unchanged. The text format forbids commas and whitespace in feature names.
  4. A4, electric-field normalization in the plasma example. Components ex, ey, ez now get the factor used for E in the je branch without the extra /1e3 that branch applies. If the /1e3 is intentional for E as well, the published e_mag, e_par and e_dot_j features must be recomputed. This is the one fix most likely to need the user's judgement.
  5. A5, reproducibility fix changes future lattices. See the behaviour-change note in section 1.
  6. A6, uncertainty thresholds. 99th percentile per node and 99.9th percentile global of the training BMU distance. Any other quantile is a one-line change in distance_quantiles.
  7. A7, thorn name and scope. AsterCurrentSheets, feature list, cadence parameter and grid-function names are proposals following the audit note; no thorn code was written.
  8. A8, stale final U-matrix kept. With history on, umat still comes from the last snapshot, for bitwise compatibility; with history off it comes from the final lattice. Logged as open issue A.
  9. A9, float64 sums in the batch trainer rather than the all-float32 path in the spec, to make results independent of device count.
  10. A10, C++ HDF5 loader deferred. The header reads the text table only; convert with SOMModel.load(...).save_text(...).

8. Not done, and why

  • No AsterX thorn source: the asterx repository was outside the editable checkout.
  • No KD-tree or early-exit BMU search: at 2368 nodes and 6 features the brute-force kernel is memory-bound once allocation is removed.
  • No connected components, temporal tracking or AMR de-duplication: the audit note places these in a later year.
  • No SCE algorithm changes beyond the two bug fixes.
  • No 20/40/80 epoch sweep for the batch budget and no GPU measurements.
  • Nothing pushed, no pull request, no README rewrite beyond fixing two undefined names in snippets.
